# Mac 与 Windows 共享文件

[文档导航](README.md) · [当前版本](../CHANGELOG.md)

本文面向 1.4.0 的四种连接方式。1.3.0 可使用 Cloudflare 和局域网共享，固定公网机器端点与 P2P 需使用新版。

每台 Mac 或 Windows 运行声笺。1.4.0 提供固定公网、CF 隧道、P2P 直连和局域网四种连接方式。可以同时配对多台机器，逐台选择目标发送文件。支持 Mac↔Windows、Windows↔Windows 和 Mac↔Mac。

Windows 需使用带“机器共享”的 1.3.0 或更新版本，Tauri 安装版和 Qt 便携版均提供入口，完整包内置 cloudflared。Mac 1.2.0 已使用相同配对/文件协议，可以继续使用。

1. 各机器选择可达的连接方式，等待就绪。固定公网和 P2P 先导入后台为本机生成的配置；P2P 需要两端均选 P2P，直连失败请手动切换方式。
2. 在 A 的“机器共享”创建邀请；在 B 点击“添加机器”粘贴邀请。邀请五分钟内有效，仅使用一次。
3. 配对后 A、B 都出现对方，可选择文件互传。继续添加 C，即可让 A 同时向 B、C 发送；B 与 C 需要各自配对后才能互传。
4. 接收任务显示进度，完成后显示校验成功，可打开接收目录。删除机器后，它无法继续向本机发送新请求；另一台机器上的配对记录需自行删除。

每对机器使用独立共享密钥和 HMAC-SHA256 请求签名，校验时间窗、随机 nonce 与请求体摘要。公网网关只转发指定手机/共享路由，不开放 `/desktop/*`。分享邀请等同临时访问凭据，只交给可信设备。

新版发送使用 1 MiB 分块，接收仍兼容旧版的 8 MiB 分块。公网 HTTPS 请求使用已有系统代理设置，局域网请求保持直连。同一发送任务遇到短暂断线会自动重试并向接收方查询已收位置。接收端保存分块状态，可承接原任务的后续请求。最终校验完整文件 SHA256 后发布到接收目录。界面上的“重新发送”会建立新任务，发送程序重启后不自动恢复旧任务。用户仍需确保接收端有足够磁盘空间。

Windows 会保存到 `%LOCALAPPDATA%/DoubaoLanInputBridge/received/`，Mac 保存在 `~/Library/Application Support/DoubaoLanInputBridge/received/`。界面提供“接收文件夹”。跨平台文件名中的 Windows 保留名称、非法字符和超长名称会调整，扩展名尽量保留；原文件内容不变。

同一局域网也可直接配对，无需开启公网。Windows 支持 10.*、172.16–31.*、192.168.* 的机器共享地址，需允许声笺的防火墙入站访问。跨网络必须让两端各自建立可访问的公网连接。机器共享只接收用户选择的文件，不自动同步剪贴板或磁盘目录。

临时域名变化时，应用尝试通过仍有效的对方地址通知新地址。如果双方同时更换域名，需重新邀请配对。固定公网/P2P 使用域名下独立的设备编号，地址在重连后保持稳定；CF 临时域名仍需维护。“已配对”表示保存了身份，不代表对方当前在线。失败任务可在确认对方在线后重新发送。

接收文件位于应用数据目录的 `received/`，未完成文件在 `incoming/`。配对信息仅保存在应用数据目录，文件权限为仅当前用户可读写，不进入源码或安装包。

## 四种连接方式

| 方式 | 手机入口 | 机器文件通道 | 条件 |
| --- | --- | --- | --- |
| 固定公网 | test.xjiaoai.com 下独立设备二维码 | 服务器中转 | 每机独立 relay.json |
| CF 隧道 | 独立临时 HTTPS 域名 | Cloudflare 隧道 | 内置 cloudflared、可访问 CF |
| P2P 直连 | 同一服务器仅认证和交换 SDP | WebRTC 数据通道 | 两端 P2P；UDP/NAT 允许打洞 |
| 局域网 | 本机当前内网地址 | 内网直连 | 同一内网、防火墙允许 |

P2P 不配置 TURN，也不自动退回服务器传文件。部分对称 NAT、企业网络和禁用 UDP 的网络无法直连。服务器保持独立的每机身份、手机口令和配对密钥；同一域名可分辨多台机器。模式切换会关闭旧入口，二维码只表示当前方式。大文件使用机器共享的分块及最终 SHA256 校验；手机单次传送上限仍为 16 MiB（建议文件小于 15 MiB）。机器文件使用接收方当前端点；选择 P2P 的发送方会拒绝向公网中转端点发送内容。
